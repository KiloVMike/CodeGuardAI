3. Problem & dataset

  • Goal: given one C function, output "vulnerable" or "not vulnerable" (binary classification on the vulnerable class = label 1).
  • Source: Devign — function-level vulnerability dataset from real C projects (FFmpeg, Qemu), released via CodeXGLUE. Labels come from commit history (vulnerable vs. fixed versions).
  • Official splits used as-is: 21,854 / 2,732 / 2,732. Splits are never merged or shuffled across.
  • Audit performed (codeguard audit): duplicate and cross-split overlap checks — train∩validation 8, train∩test 4, validation∩test 1 functions in common (out of thousands; reported honestly, never silently removed).
  • Why it's hard: noisy function-level labels (a function is marked vulnerable even if the bug is elsewhere), long functions (over half exceed 400 tokens → truncated), heavy class ambiguity, and no line-level ground truth.
  • Tokenization: CodeBERT BPE tokenizer; max_length = 400 chosen as the accuracy/throughput trade-off for this CPU (benchmark at 128 tokens vs 400 tokens; 400 keeps more context, still fits RAM).
Answer to "why 400 tokens?": it was benchmarked, not guessed. At 400 tokens the encoder runs 3.91 samples/s (full study ≈ 85 min on this CPU), and longer sequences would double runtime for functions where the vulnerability signal is usually local. The truncation rate (55.7%) is reported openly as a limitation.

4. Method — what the model actually is

4.1 Pipeline (one function)

source code
   │  CodeBERT tokenizer (max 400 tokens)
   ▼
token ids + attention mask
   │  FROZEN CodeBERT encoder  (125M params, torch.no_grad — weights never updated)
   ▼
last_hidden_state  (400 × 768)
   │  masked mean pooling  (average token vectors, ignoring padding)
   ▼
one 768-d vector
   │  standardization (running mean/std, stored in the checkpoint)
   ▼
 TRAINED HEAD  (LayerNorm, 768 → 512 → 128 → 2, GELU, dropout 0.2)
   │  softmax over 2 classes
   ▼
P(vulnerable)  ──≥ threshold 0.33──►  "Potentially Vulnerable"

4.2 Mean pooling formula

h = Σᵢ (maskᵢ · hiddenᵢ) / Σᵢ maskᵢ   for i over the 400 token positions

Padding tokens (mask = 0) are excluded, so the vector represents the actual code content only.

5. Experimental protocol (the part that earns marks)

  1. Selection rule (frozen in advance): rank experiments by validation ROC-AUC, tie-break by tuned F1, then recall. Implemented in code (_selection_key), not chosen by hand.
  2. Threshold rule (frozen in advance): grid 0.05 → 0.95 step 0.01 (91 points); maximize F1, tie-break: higher recall → fewer false negatives → closest to 0.50.
  3. Ensemble rule (frozen in advance): average probabilities of the top two models; keep it only if it beats the single best model's tuned F1 on validation. Result: rejected — honest negative result.
  4. Standardization: head input uses running mean/std computed during training, stored as buffers in the checkpoint (set_statistics) so inference never leaks training data stats.
  5. Freeze: codeguard finalize writes the bundle (weights + tokenizer + encoder + specs), records SHA-256 hashes of every checkpoint, then verify_bundle re-hashes on every load.
  6. One-time test: codeguard evaluate writes test_opened.json; if evaluation is re-run it just re-displays stored results — no second look, no tuning afterwards.
  7. Smoke vs research: quick mode uses a separate namespace (artifacts/cpu_v3/smoke/) and is never reported as a research result.

The one awkward number — own it before they ask.
At the frozen threshold, selected accuracy (53.2%) is below the majority guess (54.1%). Why: the threshold (0.33) was chosen on validation data only, by the pre-registered rule "maximize F1, then recall" — the right objective when 46% of test functions are vulnerable. That operating point deliberately casts a wide net (recall 93%). A model that flags everything has F1 = 0 and never catches anything by luck; our model has F1 0.647, catches 1171/1255, and its threshold-free ROC-AUC (0.656) beats baseline (0.621) and the trivial 0.5. The threshold was frozen before the test set was opened, so no number here was chosen to look good.
Interpretation in one line: the model is a high-recall screening tool — it flags more code than it must (precision 0.495) so that almost nothing vulnerable slips through (84 misses vs 678 for the baseline). For a first-pass security triage tool that is the correct trade; the operating point can be moved without retraining.

7. Explainability (token occlusion)

  • For a prediction, each token position is replaced with the mask token in batches; the drop in P(vulnerable) measures that token's signed influence.
  • Influences are summed per source line → top lines ranked by |influence| (default top 10).
  • Positive influence = removing the token lowered the score (token pushed toward vulnerable); negative = it pushed toward safe.
  • Explanation targets the predicted class (not always class 1).
  • Honest limits: it is an influence explanation, not a guaranteed vulnerability location — the dataset has no line-level ground truth to verify against. Scores are uncalibrated softmax outputs, not security guarantees.

8. The demo (live UI)

  • Run: run_demo.bat (or codeguard demo --open); binds to http://127.0.0.1:7860, auto-falls back to the next free port if busy.
  • Loads the frozen bundle, verifies all SHA-256 hashes, prints the URL, opens the browser.
  • Features: code editor (C), one-click examples (analysis runs on click), verdict badge with probability bar, metrics summary, line-by-line influence table, machine-readable JSON, Clear button.
  • Error handling: empty input, non-string, >200k characters and internal errors all produce a friendly panel — never a raw traceback. Queue is limited so double-clicks are safe.
  • Everything runs locally: 127.0.0.1 only, no cloud, no external API.

12. Limitations & future work

Limitations (admit first)

  • 55.7% of train functions are truncated at 400 tokens.
  • Function-level labels are noisy — some "vulnerable" functions have no local bug.
  • Encoder frozen → accuracy ceiling below full fine-tuning (~62% in literature).
  • Precision 0.495 at the chosen threshold → ~half of flags are false alarms.
  • Explanations are influences, not verified vulnerability locations.
  • Dataset bias: only FFmpeg/Qemu; may not generalize to other C projects.

Future work (the standard answers)

  • GPU → fine-tune CodeBERT end-to-end; hyperparameter sweeps on validation.
  • Long-context handling (400-token truncation): sliding windows or longer-context models.
  • Probability calibration (temperature scaling) and cost-sensitive thresholds per use case.
  • Code-specific encoders, data augmentation, cross-project evaluation.
  • Line-level attribution validated against real CVE patches.

"Software vulnerabilities in C are common and manual review is slow, so I built a system that flags vulnerable functions automatically. 16. Glossary (one-line definitions)

Transfer learningreuse a pretrained model's representations for a new task; here the encoder is frozen and only the head trains.
Fine-tuningupdating the pretrained weights themselves — we do NOT do this.
Linear probea single linear layer trained on frozen features; measures feature quality alone.
Mean poolingaveraging token vectors (ignoring padding) into one vector per function.
Precisionof the functions flagged, how many were truly vulnerable (1171/2365 = 0.495).
Recallof truly vulnerable functions, how many were caught (1171/1255 = 0.933).
F1harmonic mean of precision and recall; the pre-registered selection objective.
ROC-AUCprobability the model ranks a random vulnerable function above a random safe one; threshold-free.
Thresholdthe probability cut-off converting a score into a decision (frozen at 0.33).
Early stoppingstop training when validation loss stops improving (patience 5 epochs).
Truncationcutting functions longer than 400 tokens (affects 55.7% of train).
Occlusionmasking one token at a time to measure its influence on the prediction.
Class imbalance54/46 split — why accuracy alone is misleading and F1/recall matter.
Leakagetest information accidentally used during development; prevented by protocol + audit.
